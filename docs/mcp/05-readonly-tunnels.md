# S5 — Read-only: туннели и диагностика

> Вход: [`00-contract.md`](00-contract.md) + этот файл + `HANDOFF.md` + скил `mcp`.
> **Единственная сессия, которой нужен обзор семи движков.** Если начнёт
> распухать — резать по живому: «туннели» (sing-box, mihomo, AWG) отдельным
> PR, «прочие движки» (usque, tgproxy, opera) + диагностика — следующим.
> Независима от S4.

## Что прочитать (≈30K — самый жёсткий бюджет волны B)

- Эталонные инструменты из S2 и, если S4 уже сделана, `tools/strategies.py`
  как более свежий образец.
- Только `grep -n "def get_status\|def status\|def is_running\|def get_traffic"`
  по: `core/singbox_manager.py`, `core/mihomo_manager.py`,
  `core/awg_manager.py`, `core/usque_manager.py`, `core/tgproxy_manager.py`,
  `core/opera_proxy_manager.py`.
- `core/diagnostics.py` — **только** `grep -n "def run\|def check"` и нужные
  диапазоны. Файл большой, целиком не открывать.
- `core/update_checker.py`, `core/blockcheck.py` (только `dpi_report`-часть:
  `grep -n "classif\|report"`).
- **Скилы движков не читать.** Здесь нужна не семантика протоколов, а форма
  статуса. Если статус непонятен — `grep` по `api/<движок>.py`, как его
  отдаёт UI.

## Что написать

```
core/mcp/tools/tunnels.py      — tunnels_status (единый), tunnel_* read-only
core/mcp/tools/diagnostics.py  — diagnostics_run, dpi_report
core/mcp/tools/updates.py      — updates_check
```

| Инструмент | Возвращает |
|---|---|
| `tunnels_status` | sing-box/mihomo/AWG/usque/tgproxy/opera одним ответом: запущен ли, какой конфиг, трафик, последняя ошибка |
| `diagnostics_run` | ping/DNS/HTTP по сервисам `core/targets.py`, конфликты процессов и окружения |
| `dpi_report` | последняя классификация DPI (`core/blockcheck.py`) — **без запуска проб** |
| `updates_check` | версии движков и доступные обновления |

### Главное решение этой сессии: один `tunnels_status`, а не семь

Модель спрашивает «что с туннелями», а не «что с mihomo». Единый инструмент
с полем `engine` в каждой записи и опциональным фильтром `engine=<имя>`
экономит её контекст и наш реестр. Детализация по одному движку — тот же
инструмент с фильтром, а не отдельное имя.

### Граница «читает / пробует»

`diagnostics_run` **выпускает трафик** (ping/DNS/HTTP) — формально это
`probes`. Решение: инструмент публикуется всегда, но:

- без разрешения `probes` выполняет только пассивную часть (конфликты
  процессов, окружение, что настроено) и честно пишет в ответе, что сетевые
  пробы пропущены и каким разрешением включаются;
- с `probes` — полный прогон.

Это тот же приём, что у b4 с `b4_watchdog` (часть действий читает, часть
пробует), и он лучше, чем прятать инструмент целиком. `dpi_report` — чистое
чтение (последний сохранённый результат), проб не запускает: запуск — это
`blockcheck_start` из S8.

## Правила

1. Тонкие обёртки, никакой новой логики (см. S4, правило 1).
2. **Секреты** здесь особенно близко: приватные ключи AWG/WARP, UUID и
   пароли sing-box/mihomo, секрет Telegram-прокси, URL подписок. Проверить
   руками, что `redact` их ловит, и **добавить их в фикстуру**
   `test_mcp_redaction.py`, а не надеяться на общий сторож.
3. Движок не установлен / не запущен — это нормальный ответ
   (`installed: false`, `running: false`), а не ошибка.
4. Обновить `test_mcp_tool_counts.py` и скил `mcp`.

## Приёмка

- Один вызов `tunnels_status` даёт модели полную картину по семи движкам и
  укладывается в лимит ответа.
- На машине без единого установленного движка ответы осмысленны.
- Ни один ключ, пароль, UUID или URL подписки не появляется в ответе.

## Грабли

- **Трафик у движков считается по-разному** (интерфейс, лог, API ядра).
  Не унифицируй цифры насильно — лучше поле `traffic: null` и `source`, чем
  красивое, но неверное число.
- **`diagnostics_run` может быть долгим.** Если прогон не укладывается в
  `mcp.limits.tool_timeout_sec` — резать набор проверок по умолчанию и дать
  параметр `checks`, а не поднимать таймаут.
- **`updates_check` ходит в сеть.** Кэш и честное «не удалось проверить» —
  обязательны; на роутере без интернета инструмент не должен подвешивать GUI.
